# pdf-toolkit website

The public landing page for pdf-toolkit — a single-page marketing/onboarding
site built with [Astro](https://astro.build) + [Tailwind CSS v4](https://tailwindcss.com),
deployed to GitHub Pages by `.github/workflows/deploy-website.yml`.

Implements `ai_plans/pdf-toolkit/specs/PDF-16_project-website.md` **Phase A**
(donors: `apps/mediakit/website`, `apps/kubewright/website`).

## Prerequisites

- Node.js 22.12+ (CI pins `22`; Astro 7 requires Node >=22.12)
- npm 10+

## Quick Start

```bash
cd website
npm install
npm run dev       # http://localhost:4321/pdf-tooling/
```

```bash
npm run build      # -> website/dist/
npm run preview    # serve the production build locally
```

## Deployment (GitHub Pages)

`.github/workflows/deploy-website.yml` builds and deploys on every push to
`main` that touches `website/**`, plus manual `workflow_dispatch`. It uses
the standard `actions/configure-pages` → build → `actions/upload-pages-artifact`
→ `actions/deploy-pages` flow, actions pinned by commit SHA — a deliberate
divergence from pdf-toolkit's tag-pinned `ci.yml`/`release.yml`, because this
workflow is the only one holding `pages: write` + `id-token: write`, and
because it is a verbatim donor copy (PLAN.md §11.1.4).

**One-time repo setup** (do this before the workflow can deploy):

1. Repo Settings → Pages → **Build and deployment → Source: GitHub Actions**.
   (The implementing agent attempted this via `gh api repos/.../pages` with
   `build_type: workflow` — check the task report for whether it succeeded;
   if not, do it manually here.)
2. Push to `main` with a change under `website/**`, or run the workflow via
   **Actions → Deploy Website → Run workflow**.
3. Site becomes available at `https://armandoherra.github.io/pdf-tooling/`.

## Current target: GitHub Pages project URL

This site is configured for the **project-pages URL**, not a custom domain
(domain registration is out of scope for this implementation — recorded as
`PLAN.md` §11.1.8):

```js
// astro.config.mjs
site: 'https://armandoherra.github.io',
base: '/pdf-tooling',
```

Because `base` is a non-root path, every internal link to a `public/` asset
(favicon, og-image, robots.txt) must be prefixed with that base at render
time — see "Base path gotcha" below. Astro's own built-in asset pipeline
(stylesheets, `astro:assets` image imports) already does this correctly on
its own; only *manually written* string paths to `public/` files need the
helper.

## Switching to a custom domain later

When a domain is registered (`PLAN.md` §11.1.8), this is the exact diff:

1. **`astro.config.mjs`** — drop `base` entirely and point `site` at the
   domain:
   ```js
   site: 'https://example.com',
   // base: '/pdf-tooling',   <- delete this line
   ```
   (Every place that currently calls `withBase()`/imports `base` from
   `src/lib/site.ts` keeps working unchanged — `import.meta.env.BASE_URL`
   just becomes `"/"` and `withBase('x.png')` becomes `/x.png`.)

2. **`website/public/CNAME`** — add a file containing exactly the domain:
   ```
   example.com
   ```
   (GitHub Pages reads this from the built artifact; since it lives under
   `public/`, Astro copies it to `dist/` unchanged on every build.)

3. **DNS** (at your registrar):
   - Apex domain: four `A` records to GitHub Pages' IPs
     (`185.199.108.153`, `.109.153`, `.110.153`, `.111.153`), or
   - Subdomain (e.g. `www`): one `CNAME` record → `armandoherra.github.io`.

4. **Repo Settings → Pages** — enter the custom domain, wait for DNS check
   to go green, then check **Enforce HTTPS**.

5. **`website/public/robots.txt` and any hardcoded `armandoherra.github.io/pdf-tooling`
   strings** (search the repo — `grep -rn "armandoherra.github.io/pdf-tooling" website/src website/public`)
   — update to the new domain. `Astro.site`-derived URLs (canonical, OG image)
   update automatically from step 1 and need no manual edits.

## Base path gotcha (`src/lib/site.ts`)

`import.meta.env.BASE_URL` reflects the configured `base` **verbatim** — with
`base: '/pdf-tooling'` (no trailing slash), `BASE_URL` is `"/pdf-tooling"`, not
`"/pdf-tooling/"`. Naively writing `` `${base}og-image.png` `` silently
produces the broken path `/pdf-toolingog-image.png` (the exact bug the
donor sites' implementations caught and documented; inherited here verbatim).
Always go through `withBase('some-public-file.ext')` from `src/lib/site.ts`
for any hand-written path into `public/`; never concatenate `BASE_URL`
directly.

## Regenerating `og-image.png`

```bash
uv run python website/scripts/generate-og-image.py
```

Renders locally with Pillow (already a declared runtime dependency) — no
network calls, no fetched fonts/logos.

## Regenerating `src/data/licenses.json`

`src/data/licenses.json` is written by `scripts/licenses.py` (PDF-02) — the
same generator that writes `THIRD_PARTY_LICENSES` at the repo root — whenever
`website/src/data/` exists:

```bash
make licenses
```

CI's `license-gate` job re-runs `make licenses` and diffs
`website/src/data/licenses.json` for drift on every push (PLAN §12 R-15).
There is deliberately **no** `website/scripts/generate-licenses-json.py` —
see PDF-16's Implementation Log for why a second generator was not written.

## Deviations from PDF-16 §D1–D12 (Phase A)

Recorded here per honesty rule 7 — every figure on this page was re-derived
at landing rather than copied from the spec. The authoritative account,
including the AC-by-AC status table, is the **Implementation Log** section of
`ai_plans/pdf-toolkit/specs/PDF-16_project-website.md`. In summary:

- **No `website/scripts/generate-licenses-json.py`.** PDF-02 already writes
  `website/src/data/licenses.json` from `scripts/licenses.py generate` once
  this directory exists. Writing a second generator would have to
  byte-exactly reproduce PDF-02's determinism apparatus and risks permanent
  drift against the real `make licenses` gate.
- **`licenses.json`'s shape is the raw `pip-licenses --format=json` array**
  (`{Name, Version, License}` objects, capitalised keys) — not the
  `{schema_version, source, packages:[...]}` envelope this spec originally
  sketched. All presentational prose (tiering, roles) lives in the `.astro`
  components, never in the data file.
- **The Verbs roster totals 26** (25 verbs from `PLAN.md` §4.1 plus
  `version`, PDF-01's already-shipped diagnostics placeholder), not the 25
  this spec's prose assumed. One entry (`version`) is `available`; the rest
  are `planned`.
- **The default install closure computed on this page is 21 packages**, not
  22 — `colorama` (Windows-only, via `typer`/`click`) is part of the
  cross-platform `uv.lock` but is not installable under the Linux/CPython
  3.11 measurement venv `make licenses` uses, and pdf-toolkit's own
  `pyproject.toml` classifiers only claim POSIX/Linux and macOS support. The
  number is computed live from `src/data/licenses.json`, never hard-coded.
- **`.github/dependabot.yml` now lists three ecosystems**: `uv:/`,
  `github-actions:/`, `npm:/website` — PDF-02 uses the `uv` ecosystem, not
  `pip`.
